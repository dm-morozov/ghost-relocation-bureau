# N1 · Защита сохранения между вкладками

## Проблема и решение

Прямой `localStorage.setItem` в App и ShiftGame мог молча заменить более свежую работу другой вкладки. По поручению пользователя AI подготовил изолированные модуль, hook, UI и тесты. App, ShiftGame, backup и общий CSS не менялись: их интегрирует основной чат по правилам владения.

`createStorageSync<T>` хранит baseline **исходного raw**, сравнивает актуальный `getItem` непосредственно перед каждой записью/удалением, обновляет baseline только после успешного собственного сохранения либо явной загрузки. `storage`-событие и проверка при установке слушателя обнаруживают изменение заранее; содержимому запоздавшего `newValue` не доверяем. После конфликта запись остаётся заблокирована даже при возвращении прежнего raw. Нет функции force overwrite. Скачивание локальной копии не снимает блокировку.

`loadFresh(apply)` повторно читает ключ, валидирует через parser вызывающей стороны и только после успешного применения принимает baseline. `null` передаётся parser как удаление. Ошибка доступа, квоты или parser оставляет сохранение защищённым. Разные ключи сессии/игры имеют независимые контроллеры.

## Файлы и API

- `src/storage-sync.ts`: `StorageBaseline`, `readStorageBaseline`, `createStorageSync<T>`, состояния ready/conflict/unavailable/invalid.
- `src/useStorageSync.ts`: `{ sync, state, blocked }`; один контроллер на mounted ключ; `useSyncExternalStore`, подписка и очистка слушателя. Опции фиксированы на mount; при смене ключа/схемы нужен remount.
- `src/StorageConflict.tsx`, `src/storage-sync.css`: именованный alert, кнопки «Скачать локальную копию» и «Загрузить свежую версию», тексты удаления/ошибок. Светлая палитра и `[data-theme='dark']`, системная тема наследует разрешённый theme. На узком экране кнопки переносятся, есть фокус и touch target 44px.
- Новые `src/storage-sync.test.ts`, `src/StorageConflict.test.tsx`.

## Точное подключение основным чатом

### 1. Boot: одно чтение и передача baseline

В `backup.loadSession` и `ShiftGame.loadGame` заменить первоначальный `getItem` на `const baseline = readStorageBaseline(KEY)`. Вернуть `baseline` вместе с boot-данными **во всех ветках**. При `!baseline.ok` вернуть временное состояние с прежней ошибкой/recovery. При `baseline.ok` парсить именно `baseline.raw`, при null брать исходное состояние. При ошибке parser сохранить baseline `{ ok: true, raw: исходный raw }`, установить прежний blocked/recovery.

Нельзя отдельно вызывать `readStorageBaseline` после `loadSession/loadGame`: между чтениями другая вкладка может изменить ключ. Нельзя выводить доступность из `boot.original === null`: это может быть и пустое хранилище, и ошибка getItem. Нужен явный `baseline.ok`. `original` для recovery сессии оставить равным прочитанному raw; прежнюю защиту recovery-копией сохранить.

### 2. App

Импортировать `useStorageSync`, `StorageConflict`, `parseSession`, `saveFile`, `makeBackup` и типы по необходимости. После `boot` вызвать:

```tsx
const {
  sync,
  state: syncState,
  blocked: syncBlocked,
} = useStorageSync<Session>({
  key: storageKey,
  baseline: boot.baseline,
  initialInvalid: boot.baseline.ok && boot.blocked,
  parse: (raw) =>
    raw === null
      ? {
          ghosts: demoGhosts(todayISO()),
          places: structuredClone(demoPlaces),
          assignments: {},
          pinned: [],
        }
      : parseSession(raw),
});
```

`demoPlaces` — импорт `places as demoPlaces` из data; не текущее React-состояние `places`. Замена autosave-effect:

```tsx
useEffect(() => {
  if (storageBlocked || syncBlocked) return;
  sync.save(JSON.stringify({ ghosts, assignments, places, pinned }));
}, [ghosts, assignments, places, pinned, storageBlocked, syncBlocked, sync]);
```

Вывести `StorageConflict` над рабочей областью со `state={syncState}`, `subject="Сессия бюро"`. `onDownloadLocal` вызывает `saveFile(makeBackup(currentSession), 'quiet-address-local.json')`, не `getItem`.

`onLoadFresh`: сначала `if (!mayLeave()) return;`, затем `sync.loadFresh(next => { restoreSession(next); setUndo(null); setStorageBlocked(false); setError(''); setMessage('Загружена актуальная сохранённая версия.'); })`. Также отменить ожидающий allocationTimer и очистить preview/подтверждения N2/N3: они относятся к прежней версии. При null этот parser явно загружает начальную демосессию; при следующем autosave она может быть сохранена, это происходит уже после выбора пользователя. При необходимости текст кнопки/подсказку для удаления уточнить на интеграции.

### 3. ShiftGame (после N5)

```tsx
const {
  sync,
  state: syncState,
  blocked: syncBlocked,
} = useStorageSync({
  key: gameStorageKey,
  baseline: boot.baseline,
  initialInvalid: boot.baseline.ok && boot.recovery,
  parse: (raw) => (raw === null ? newGame() : parseGame(raw)),
});
useEffect(() => {
  if (recovery || syncBlocked) return;
  sync.save(serializeGame(state));
}, [state, recovery, syncBlocked, sync]);
```

Показать `StorageConflict` рядом с intro: `subject="Ночная вахта"`. Скачать **локальный** `serializeGame(state)` через `saveFile(..., 'quiet-address-game-local.json')`. Загрузка: `sync.loadFresh(next => { setState(next); setRecovery(false); setError(''); setPreview(false); setRestart(false); })`. Проверить актуальный API после N5. Здесь null означает новую игру; повреждённая свежая игра не заменяется новой автоматически.

### 4. Все пути записи, reset/recovery и отмена

После подключения найти все записи/удаления **этих двух ключей**, включая `resetSavedSession`/`preserveSavedSession` и callbacks SessionTools. Сначала `sync.check()`, при false остановить сценарий. После сохранения recovery-исходника удалять основной ключ через `sync.save(null)` и проверять результат; не оставлять обходной `localStorage.removeItem`. При уже существующем конфликте ни reset, ни импорт, ни перезапуск игры не должны разблокировать sync. Экспорт доступен всегда. Исходный повреждённый raw должен по-прежнему сохраняться в recovery до разрешённой замены; новый модуль не заменяет эту механику.

Для первоначально повреждённого boot sync намеренно заблокирован: прежняя кнопка «заменить повреждённую сессию» не должна обходить защиту. На интеграции приоритет — экспорт исходника/локальной работы и загрузка валидной свежей версии; для сохранения прежнего сценария восстановления нужен отдельный явно подтверждённый протокол с recovery-копией и перепроверкой raw, а не новая функция force overwrite. Не объявлять прежний reset работающим, пока этот путь не согласован и не проверен.

`syncBlocked` в UI — только отображение/предварительный запрет. Именно `sync.save/check` является защитой от изменения между последним render и действием пользователя. Undo после загрузки свежей версии очищается, иначе он легко вернёт устаревшую версию поверх принятой свежей.

## Ограничения и остаток

Это готовые локальные модули, **ещё не интегрированная защита приложения**. Проверка в двух настоящих вкладках и визуальная приёмка трёх тем/320/390px — после интеграции. Полную сборку/общий набор тестов основной чат запускает после объединения потоков. Commit/push/deploy не выполнялись.

`localStorage` не предоставляет атомарный compare-and-swap: две физически одновременные записи могут обе пройти compare до setItem. Это optimistic compare-before-save, не гарантия транзакционной совместной работы. Для строгого исключения такой гонки потребуется общий протокол блокировки (например Web Locks с определённой политикой fallback) или другое хранилище. ABA без доставленного события тоже неразличим при сравнении raw; UI не заявляет real-time collaborative editing.
