# N3 · Быстрое назначение сохранённого дома

## Проблема

После создания дома для конкретной заявки интерфейс предлагал только возврат; оператору приходилось отдельно выбирать адрес. Проверка любого подходящего места в App также не связывала предложение с только что сохранённым домом.

## Решение и реализация

Авторское требование: быстро назначить сохранённый дом, повторно проверить условия и вместимость, сохранить ручное закрепление и отмену. AI реализовал изолированный `IdealPlaceAction`: принимает актуальные `ghost`, `place`, `assignments`, `today`, `onOpenRequest(ghostId)` и `onAssign(ghostId, placeId)`. `onAssign` отвечает за назначение и переход в родителе; компонент не вызывает второй callback после назначения.

`relocation.conflicts` вызывается на каждом рендере и непосредственно при нажатии. Завершённая заявка блокируется дополнительно по `settledAt`. Отказ при нажатии вызывает повторный рендер с актуальной причиной; обхода конфликта нет. Возврат к заявке доступен при любом конфликте. Компонент использует существующие `notice`, `primary`, `secondary`, поэтому следует общей теме. CSS переносит длинные названия, кнопки занимают всю ширину на узком экране, минимальная высота 44px.

Файлы: `src/IdealPlaceAction.tsx`, `src/ideal-place-action.css`, `src/IdealPlaceAction.test.tsx`. App/PlaceForm и публичный Worklog этим чатом не изменялись.

## Точное подключение в App (выполняет основной чат)

1. Импорт и отдельный ID сохранённого адреса рядом с существующим `idealFor`:

```tsx
import IdealPlaceAction from './IdealPlaceAction';

const [idealPlaceId, setIdealPlaceId] = useState<string | null>(null);
const idealGhost = ghosts.find((g) => g.id === idealFor);
const idealPlace = places.find((p) => p.id === idealPlaceId);
```

2. В `createIdealPlace(g)` сразу после `setIdealFor(g.id)` добавить `setIdealPlaceId(null)`. Везде, где контекст очищается через `setIdealFor(null)`, очищать и `setIdealPlaceId(null)`. При загрузке/импорте/замене сессии также очищать оба ID, чтобы не показывать старое предложение для случайно совпавших ID. Текст инструкции в конце `createIdealPlace` заменить:

```tsx
setMessage(
  `Параметры для ${g.name} заполнены. Проверьте их и сохраните дом, затем назначьте его заявке.`,
);
```

3. В **ветке создания** `PlaceForm.onAdd`, после существующих проверок доступной иллюстрации и лимита, сохранить текущие `setUndo`, `setPlaces`, закрытие формы и `finishForm`; перед `setMessage` добавить:

```tsx
setIdealPlaceId(idealFor ? p.id : null);
setMessage(
  idealFor
    ? 'Дом сохранён. Проверьте условия и назначьте его заявке.'
    : 'Место добавлено. Перейдите в заявки и повторите подбор, чтобы использовать новый адрес.',
);
```

Это заменяет прежний `setMessage`, а не добавляет второй. Не назначать дом внутри `onAdd`: оператор сначала видит результат проверки. Если основной чат сохраняет сценарий «все локации добавлены → изменить существующее место», в ветке редактирования после `setPlaces` также добавить `setIdealPlaceId(idealFor ? p.id : null)`; предложение относится именно к сохранённому адресу.

4. Заменить прежний блок `{idealFor && ... places.some(...) && (...)}` целиком:

```tsx
{
  idealGhost && idealPlace && !showPlaceForm && (
    <IdealPlaceAction
      key={`${idealGhost.id}:${idealPlace.id}`}
      ghost={idealGhost}
      place={idealPlace}
      assignments={assignments}
      today={today}
      onOpenRequest={(id) => {
        if (!select(id, true)) return;
        setTab('Заявки');
        setIdealFor(null);
        setIdealPlaceId(null);
      }}
      onAssign={(id, placeId) => {
        // Проверка границы изменения состояния, включая актуальные записи и дату.
        const request = ghosts.find((g) => g.id === id);
        const home = places.find((p) => p.id === placeId);
        if (!request || !home || request.settledAt) return;
        const conflicts = relocation.conflicts(request, home, assignments, today);
        if (conflicts.length) {
          setError(conflicts.join('; '));
          return;
        }
        // select проверяет mayLeave ДО изменения и не трогает undo.
        if (!select(id, true)) return;
        apply(id, placeId);
        // select использует старые assignments: явно выбираем новый адрес.
        setTarget(placeId);
        setTab('Заявки');
        setIdealFor(null);
        setIdealPlaceId(null);
      }}
    />
  );
}
```

`apply()` уже делает `setUndo(structuredClone(currentSession))`, обновляет `assignments`, добавляет ID в `pinned` и очищает `pending`. Не дублировать эти операции и не вызывать автоподбор. Undo после быстрого назначения возвращает состояние **после создания дома, до назначения**; ранее существовавшие назначения/замочки восстанавливаются, созданный дом остаётся. Это два отдельных осознанных действия. При интеграции N1 добавить к callback ту же защиту от записи устаревшей сессии, что и у остальных мутаций; `select` не заменяет межвкладочную защиту.
